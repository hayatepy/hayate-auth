## Scheme-bound cookie acceptance

v0.10.1 set Secure `__Host-` cookies on HTTPS, but readers still fell back to
the corresponding bare cookie name. That fallback weakened the isolation
property when a valid bare signed value reached an HTTPS request. v0.10.2
makes cookie acceptance depend exclusively on the trusted request URL scheme:

- HTTPS accepts only the `__Host-` name.
- Plain HTTP accepts only the bare local-development name.
- Session, provider OAuth state, authorization consent, passkey challenge, and
  two-factor challenge flows share the same fail-closed reader.
- Cross-scheme regression tests cover every cookie name, the complete session
  path, and the provider OAuth callback without relying on browser behavior.

The library reads the WHATWG request URL; it does not trust forwarded headers
itself. A reverse proxy or adapter must construct the externally correct URL
from a trusted transport boundary and must reject spoofed forwarding metadata.
Allowing an attacker to make an HTTPS request appear as HTTP intentionally
selects the weaker local-development cookie namespace and is outside the
documented production profile.

## Retained v0.10.1 security scope

The DPoP enforcement, token revocation/introspection, consent concurrency,
password policy, session management, TOTP single-use, and adapter atomicity
scope recorded by the v0.10.1 amendment remains in the complete v0.10.3 target.
The selected ASVS ledger remains 50 covered / 3 external / 0 gap; the cookie
rows now cite the scheme-bound acceptance regressions in addition to issuance
attributes.

## Residual and delegated risks

- DPoP remains opt-in. The default Bearer profile remains replayable after
  token disclosure.
- Server-provided DPoP nonce challenges are not implemented.
- All replicas and isolates must share an atomic replay store.
- A top-3000 policy-matching password set and current breach corpus remain
  deployment inputs; the compact built-in baseline is not presented as ASVS
  coverage.
- Rate limiting, trusted proxy URL reconstruction, recoverable-secret
  protection, administrative authorization, production Cloudflare
  configuration, TLS, logging, backup policy, and tenant isolation remain
  deployment responsibilities.
- PostgreSQL remains generated schema/migration coverage, not a shipped
  runtime adapter.

## Required reviewer treatment

Reproduce Profiles A–D in `audit/PROCEDURES.md`, inspect the complete
v0.9.1-to-v0.10.3 range, and focus manual review on the scheme/cookie boundary
as well as the earlier security deltas. Add adversarial tests rather than
accepting the maintainer suite as an audit conclusion. Findings and the final
report must identify v0.10.3 by tag and commit and distinguish library,
configured-profile, proxy, and deployment responsibilities.
