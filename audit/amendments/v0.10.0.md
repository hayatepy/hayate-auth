# v0.10.0 security-review amendment

This amendment moves the active review target from the signed v0.9.1 base to
the signed v0.10.0 release without rewriting the historical base. Reviewers
must evaluate v0.10.0 as a whole, using v0.9.1 only as the code-review baseline
and prior threat-model snapshot. No independent finding or assurance is
inherited merely because a control existed in the base.

## Immutable release identity

- Base: `v0.9.1` at `b8486cf40cfa227b44062ee41bddb4a6b74132fa`
- Review target: `v0.10.0` at
  `b885e066355196c9caeedb0819eee03fc4d119ed`
- Range: `v0.9.1..v0.10.0`

Both annotated tags, their signing fingerprints, PyPI artifacts, and the
v0.10.0 SPDX SBOM are pinned in TOML and verified by
`scripts/check_audit_pack.py`. The GitHub v0.10.0 release is immutable.

## Security-relevant delta

| Area | New boundary in v0.10.0 | Priority review question |
|---|---|---|
| TOTP | The last accepted time step is persisted with guarded atomic consumption | Can replay, an adjacent-window code, rollback, or a concurrent request obtain two sessions? |
| Password policy | A shared local/injected compromised-password decision gates sign-up, reset, and change | Do timeout, checker failure, normalization, or account existence change state or leak identity? |
| Sessions | Idle expiry, bounded activity writes, fresh-session checks, listing, and owner-scoped revocation | Can a stale or cross-user session enumerate tokens, survive revocation, or race an activity touch? |
| OAuth revocation | RFC 7009 revokes a complete family without validity disclosure | Can refresh/code races expose a live replacement after revocation? |
| Introspection | RFC 7662 requires a separate resource-server credential and exact resource binding | Can one resource inspect another audience, or can failure become fail-open? |
| Consent | Users can list and revoke grants backed by a generation counter | Can concurrent code exchange or refresh outlive consent revocation? |
| DPoP | Opt-in RFC 9449 ES256 binding covers code, access token, public refresh token, resource request, and introspection | Are proof parsing, key/thumbprint binding, `htu`/`htm`/`ath`, time, and shared replay storage fail-closed on CPython and Workers? |
| Storage schema | Session activity, TOTP replay state, grant generation, resource credentials, and DPoP replay records extend existing tables | Are v0.9.1 migrations correct and atomic on SQLite, PostgreSQL DDL, and D1? |

## Residual and delegated risks

- Rate limiting and anti-automation remain deployment controls.
- TOTP seeds and upstream provider tokens remain recoverable secrets.
- The built-in password blocklist is a deterministic baseline smaller than
  ASVS's top-3000 threshold; a compliant set and current breach corpus remain
  injected deployment inputs.
- DPoP is opt-in. Bearer remains the stable MCP compatibility default.
- Although `DPoPConfig.require_bound_tokens` exists, the signed target does
  not contain selected regression evidence for server-wide DPoP-only
  issuance; the ASVS sender-constraint row remains a gap.
- DPoP nonce challenges are not implemented; the replay store, bounded proof
  age, `ath`, exact request binding, and HTTPS define the supported profile.
- Email magic links remain a convenience authenticator and are not claimed as
  an ASVS Level 3 factor.
- PostgreSQL coverage remains schema application only; no PostgreSQL runtime
  adapter is shipped.
- Production Cloudflare configuration, secret bindings, rate limiting,
  logging, TLS, backup policy, and tenant isolation remain outside local
  workerd/D1 reproduction.

## Required reviewer treatment

Reproduce every profile in `audit/PROCEDURES.md`, inspect the complete release
range, and add adversarial tests around each delta above. Findings must name
whether they affect the v0.9.1 base, the v0.10.0 delta, or an integration
boundary. The final report and public summary must identify v0.10.0 by tag and
commit; reviewing only the changed files is not sufficient for a production
assurance conclusion.
